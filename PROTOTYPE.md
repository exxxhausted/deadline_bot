Этот файл не является техническим заданием. Он описывает, куда мы идём и что уже решено, а то, что пока неизвестно, честно вынесено в раздел «Открытые вопросы». Бота ещё нет, поэтому многие детали нельзя придумать заранее — их нужно выяснить в процессе. Считай этот файл основным источником контекста при работе над проектом. Если в коде или более новых решениях команды что-то изменилось, сначала сверь расхождение и предложи обновить этот файл.

**Текущий этап: 0.** Собран телеграм эхо-бот. Проверка альтернативных возможностей

## Что мы делаем

«Дедлайн-бот» — Telegram-бот для учёта учебных задач. Пользователь добавляет задания с датами сдачи, просматривает их, меняет статус и получает напоминания. Главная цель — быстро фиксировать дедлайны и не держать их в голове.

Проект делается как учебный командный проект на C++. Приоритет — рабочий, понятный прототип, а не большое приложение со множеством функций. Для автора проекта так же важно, чтобы код оставался его собственным: каждый фрагмент должен быть понятен тому, кто его пишет.

## Вектор развития

Это ориентир, а не расписание. Каждый этап даёт запускаемый результат, и следующий начинается, когда предыдущий работает.

0. **Эхо-бот.** Программа получает сообщение из Telegram и отвечает тем же текстом. Цель — проверить транспорт (HTTPS-запросы, JSON, получение обновлений) и снять главную неопределённость проекта.
1. **Ядро в консоли.** `Task`, `TaskStatus`, `TaskService`, InMemory-репозиторий, временный консольный интерфейс, тесты. Всё на стандартном C++ и STL, без Telegram и SQLite.
2. **Парсер.** Разбор строки вида `Лабораторная по ОС, 18.11.2026` в `TaskDraft`, с тестами на ошибки и граничные случаи.
3. **Подключение ядра к Telegram.** Команды `/start`, `/add`, `/tasks`, `/task <id>`, inline-кнопки, диалог подтверждения.
4. **SQLite.** Второй репозиторий вместо InMemory; задачи сохраняются между перезапусками.
5. **Напоминания.** Фоновая проверка и отправка за ~24 часа до дедлайна.

## Целевое поведение (MVP)

Это то, к чему стремимся. Точное поведение уточняется по мере реализации.

- `/start` — приветствие и краткая инструкция.
- Добавление задачи: название и дата дедлайна.
- Список незавершённых задач с датами и статусами.
- Просмотр отдельной задачи.
- Изменение названия и дедлайна.
- Удаление задачи.
- Смена статуса: `planned`, `in_progress`, `completed`.
- Сохранение задач в SQLite между перезапусками.
- Быстрый ввод одной строкой с разбором даты через регулярные выражения.
- Одно автоматическое напоминание примерно за 24 часа до дедлайна для незавершённой задачи.

## Основной пользовательский сценарий

1. Пользователь открывает бота и отправляет `/start`.
2. Для добавления выбирает «Добавить задачу» или отправляет `/add`.
3. Вводит строку, например: `Лабораторная по ОС, 18.11.2026`.
4. Бот пытается выделить название и дату, показывает результат и просит подтвердить.
5. Если дата не распознана или некорректна, бот предлагает ввести её отдельно.
6. После подтверждения задача сохраняется.
7. Через «Мои задачи» или `/tasks` пользователь видит незавершённые задачи и может открыть нужную, изменить её, удалить или сменить статус.

Основные команды: `/start`, `/add`, `/tasks`, `/task <id>`. Для действий с задачей можно использовать inline-кнопки.

## Технологии

| Область | Технология |
|---|---|
| Язык | C++23 |
| Сборка | CMake |
| Telegram | cpr + nlohmann/json |
| База данных | SQLite 3 |
| C++-обёртка для SQLite | SQLiteCpp |
| Быстрый ввод | `std::regex` |
| Тесты | Catch2 |
| Версионирование | Git, GitHub |
| Зависимости | CMake FetchContent |

Токен Telegram нельзя хранить в исходном коде или коммитить в репозиторий. Используй переменную окружения:

`[System.Environment]::SetEnvironmentVariable('TELEGRAM_BOT_TOKEN','123456789:AA...ваш_токен...','User')` - на Windows

или

`echo 'export TELEGRAM_BOT_TOKEN="123456789:AA...ваш_токен..."' >> ~/.bashrc
&& source ~/.bashrc` - на Linux

## Архитектура и границы компонентов

Вариант — модульный монолит: одно приложение, разделённое на компоненты. Микросервисы, отдельный backend и веб-интерфейс не нужны.

Структура проекта:

```text
deadline_bot/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   ├── model/        # Task, TaskStatus, TaskDraft, TaskService,
│   │                 # интерфейс TaskRepository, Parser
│   ├── repo/         # InMemoryTaskRepository, SqliteTaskRepository
│   ├── view/         # клиент Telegram Bot API (отправка и получение сообщений)
│   └── presenter/    # команды, обработчики сообщений и кнопок, управление диалогом
└── tests/
```

Что есть что:

- **model** — предметные типы и правила (`Task`, `TaskStatus`), операции с задачами (`TaskService`), интерфейс `TaskRepository` и независимый `Parser`, разбирающий пользовательскую строку в `TaskDraft`.
- **repo** — реализации `TaskRepository`: InMemory (для тестов и раннего этапа) и SQLite.
- **view** — взаимодействие с Telegram API. На раннем этапе допустим временный консольный интерфейс.
- **presenter** — принимает пользовательский ввод, вызывает `TaskService`, формирует ответ.

Правила зависимостей:

- `model` не знает ни о `repo`, ни о `view`, ни о `presenter`; интерфейс `TaskRepository` принадлежит `model`.
- Telegram-обработчики не содержат SQL и основную бизнес-логику.
- Парсер не зависит от Telegram и базы данных.
- Repository работает с предметными типами, а не с Telegram-сообщениями.

Где живёт фоновая проверка напоминаний — см. «Открытые вопросы».

## Модель задачи и хранение

Основная сущность — `Task`. В ней нужны как минимум:

- `id` — идентификатор задачи;
- `user_id` — Telegram ID владельца;
- `title` — название;
- `deadline` — дата сдачи;
- `status` — `planned`, `in_progress` или `completed`;
- `created_at` — время создания записи;
- `reminder_sent` — отправлено ли напоминание.

Для MVP достаточно одной таблицы `tasks`. Дедлайн хранится как дата в формате `YYYY-MM-DD`; отдельное время сдачи пока не поддерживается.

`user_id` нужен с самого начала, даже если при локальной разработке используется один тестовый аккаунт. Все операции чтения и изменения по `id` должны дополнительно проверять владельца задачи. Данные разных пользователей нельзя смешивать.

Это базовый ориентир: дополнительные поля и точные интерфейсы нужно согласовывать между участниками, а не добавлять произвольно в разных компонентах.

## Быстрый ввод: regex

Быстрый ввод нужен, чтобы сократить число действий пользователя. Поддерживаемый пример:

```text
Лабораторная по ОС, 18.11.2026
```

Ожидаемый результат:

```text
title = "Лабораторная по ОС"
deadline = 2026-11-18
```

На первом этапе поддерживаем дату `ДД.ММ.ГГГГ`. Формат `ДД.ММ` — под вопросом (см. «Открытые вопросы»).

Правила парсера:

- regex выделяет фрагмент даты, но календарная корректность проверяется отдельно;
- дата вроде `31.02.2026` должна быть отклонена;
- название получается из оставшейся части строки после удаления даты и разделителей;
- при отсутствии даты, ошибке или неоднозначности возвращается неполный результат/ошибка, после чего бот просит уточнение;
- парсер принимает строку и при необходимости текущую дату явным параметром; он не обращается напрямую к Telegram, SQLite или системным часам;
- результат — `TaskDraft` или аналогичный тип результата с ошибкой.

Словесные даты (`«послезавтра»`, `«в следующий четверг»`), время, сложность и важность в MVP не входят. Не нужно пытаться угадывать данные, которых пользователь явно не указал.

## Напоминания

Для незавершённой задачи планируется одно напоминание примерно за 24 часа до дедлайна. Фоновый компонент периодически проверяет задачи и отправляет уведомления через Telegram.

- Выполненные задачи не напоминаются.
- `reminder_sent` выставляется только после успешной отправки сообщения через API.
- При временной ошибке отправки задача не должна преждевременно помечаться как напомненная; следующая проверка должна дать возможность повторить попытку.
- При изменении дедлайна состояние напоминания нужно сбросить/пересчитать.

Точное время отправки и правило часового пояса не определены — см. «Открытые вопросы».

## Открытые вопросы

Эти вопросы сознательно не решаются заранее: пока нет работающего бота, любое решение будет догадкой. К каждому возвращаемся на указанном этапе. Нельзя реализовывать поведение по такому пункту, не записав здесь выбранное решение.

| Вопрос | Когда решаем | Заметки |
|---|---|---|
| Время и часовой пояс напоминаний | перед этапом 5 | Вариант на обсуждение: напоминать в фиксированный час (например, 09:00) за день до даты сдачи, часовой пояс — из конфигурации. Что делать с задачей, добавленной менее чем за 24 часа до дедлайна? |
| Формат `ДД.ММ` без года | этап 2 | Либо убрать из MVP, либо задать правило для прошедших дат |
| Можно ли добавлять задачи с датой в прошлом | этап 2 | |
| Видимость завершённых задач | этап 3 | Сейчас `/tasks` показывает только незавершённые; как возвращать или удалять `completed`? Возможно, нужен `/tasks all` |
| Хранение состояния диалога (подтверждение, ввод даты отдельно) | этап 3 | В памяти или в БД; что происходит при перезапуске |
| Потоки и SQLite | этап 4–5 | Напоминания можно сначала сделать простой проверкой в основном цикле без отдельного потока; решение о потоках принимаем, только если это станет необходимо |
| Расположение фонового компонента напоминаний | этап 5 | Вероятно, `presenter` или отдельный модуль; в `view/` не должен попасть код бизнес-логики |
| Нумерация `id` | этап 3–4 | Глобальный autoincrement или номер в пределах пользователя |
| Формат хранения `created_at` | этап 4 | UTC, ISO-8601 или Unix-время |
| Миграции схемы | этап 4 | Минимум — `PRAGMA user_version` |
| Сообщения об ошибках из `TaskService` | этап 1 | В C++20 нет `std::expected`; варианты: свой `Result<T>`, `std::optional` + код ошибки, исключения |
| Парсер: запятая как разделитель | этап 2 | Название может содержать запятые; возможное правило — дата всегда в конце строки, остальное название. Regex, вероятно, стоит применять только к цифровой дате |
| Имя переменной окружения для токена | этап 0 | Например, `DEADLINE_BOT_TOKEN`; добавить `.env.example` без секрета |
| Версии зависимостей | этап 1 | Закрепить теги или коммиты для FetchContent |

## Правила совместной разработки

- Сначала согласуем `Task`, `TaskStatus`, `TaskDraft` и интерфейс `TaskRepository`.
- Публичные интерфейсы не меняются без обсуждения.
- Repository работает с предметными типами, а не с Telegram-сообщениями.
- Парсер не знает о Telegram и SQLite.
- Каждый компонент делается в отдельной Git-ветке и отправляется через pull request.
- Автор проекта интегрирует компоненты; второй участник проверяет интеграцию и исправляет ошибки своего модуля. Кто ревьюит pull request'ы других модулей — договориться (см. открытые вопросы при начале командной работы).
- Если задача пока слишком сложная для второго участника, её можно уменьшить до тестов, набора тестовых данных, проверки сценариев или документации. Не нужно искусственно создавать модули ради формального распределения кода.

## Что пока не делать

Не добавляй без отдельного решения команды:

- сложные приоритеты и оценку трудозатрат;
- heatmap и другие расширенные визуализации;
- Pomodoro, статистику продуктивности и геймификацию;
- Google Calendar и другие календарные интеграции;
- совместные проекты, команды, участников и права доступа;
- веб-интерфейс или отдельное мобильное приложение;
- повторяющиеся задачи и несколько напоминаний на задачу.

Это возможные направления развития, но сейчас они отвлекают от рабочего ядра.
